# Document Types

文書種別は固定テンプレートではなく、読者が最初に必要とする情報と、残すべき材料を判断するために使う。

## Technical article

目的:
読者が問題を理解し、同じ方法を試すか避けるか判断できるようにする。

優先:
- 扱う問題や問いを早めに示す
- 手順だけでなく採用理由と適用条件を残す
- 事実、観測、推測を区別する
- 実測していない効果を断定しない

よくある失敗:
一般論から始まり、本題までが長い。

## Design note / ADR

目的:
判断の背景、制約、選択肢、決定を後から追えるようにする。

優先:
- なぜ今決めるか
- 採用案
- 代替案
- 判断理由
- 制約
- リスクと未決事項

よくある失敗:
一般的なベストプラクティスだけで、今回の制約が見えない。

## PR description

目的:
レビュアーが変更理由、差分、影響範囲、確認方法を短時間で把握できるようにする。

優先:
- なぜ変えたか
- 何が変わったか
- どこを見てほしいか
- どう検証したか
- 対象外や未確認範囲

よくある失敗:
実装ログを時系列で並べ、レビュー判断に必要な情報が埋もれる。

## Issue

目的:
問題、期待する状態、作業境界を共有する。

優先:
- 現状
- 問題
- 完了条件
- 対象範囲
- 必要なら制約

よくある失敗:
解決策を先に固定し、何を解決したいかが見えない。

## Review comment

目的:
相手が問題と理由を理解し、修正判断できるようにする。

優先:
- 指摘対象
- 問題が起きる理由
- 影響
- 必要なら修正案

よくある失敗:
「可読性」「保守性」のような抽象評価だけで終わる。

## Internal announcement

目的:
対象者が変更内容、影響、必要な行動を理解する。

優先:
- 誰が対象か
- 何が変わるか
- いつからか
- 何をする必要があるか
- 例外や問い合わせ先

よくある失敗:
丁寧な前置きが長く、必要な行動が遅い。

## Operation guide

目的:
読者が安全に作業を完了できるようにする。

優先:
- 前提
- 手順
- 成功条件
- 失敗時の確認
- ロールバックや中止条件

よくある失敗:
理由説明と実行手順が混ざり、手順だけ追えない。

## Report

目的:
事実・分析・判断材料を共有し、次の意思決定につなげる。

優先:
- 結論や重要な発見
- 根拠
- 解釈
- 制約
- 次の判断

よくある失敗:
調査した順に書かれ、何が重要か見えない。

## Research note

目的:
調べたことと未確認事項を再利用可能な形で残す。

優先:
- 問い
- 分かったこと
- 根拠
- 不明点
- 次に確認すべきこと

よくある失敗:
検索結果の要約集になり、自分が何を確認したかったか消える。

## Meeting minutes

目的:
決定、未決事項、担当、次のアクションを後から追えるようにする。

優先:
- 決定事項
- アクション
- 担当
- 期限
- 保留事項
- 必要な議論経緯

よくある失敗:
会話を時系列で忠実に再現し、決定が埋もれる。

## Release note

目的:
利用者が変更内容と自分への影響を理解する。

優先:
- 利用者から見える変更
- 互換性
- 移行
- 制約
- 必要な操作

よくある失敗:
内部実装の説明が中心になり、利用者への影響が見えない。

## Email

目的:
相手が内容を理解し、必要なら返信や行動を取れるようにする。

優先:
- 用件
- 必要な背景
- 依頼
- 期限
- 補足

よくある失敗:
礼儀を優先しすぎて、依頼内容や期限が後ろへ埋もれる。

## General

既存型に無理に当てはめない。

読者が最初に知りたいこと、保持すべき材料、読後に必要な行動から構成を決める。
