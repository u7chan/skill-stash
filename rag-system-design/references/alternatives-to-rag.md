# RAG以外の選択肢

「知識をLLMに使わせたい」ことと「RAGを作る」ことは同じではない。

質問とデータの性質に応じて、より単純な方式を優先する。

## 全文をそのまま渡す

対象資料がモデルのcontextへ無理なく収まり、応答時間とコストも許容できるなら有力。

向いている場面:

- 資料が少ない
- 全体を見て答える質問が多い
- 複雑なindex運用を持ちたくない
- 同じ資料を繰り返し使える

確認すること:

- context上限
- token cost
- latency
- cacheなどの再利用性
- 全文を入れても重要箇所を見落とさないか

固定のページ数を万能な境界にしない。

## その場検索

事前にembedding indexを作らず、質問時に正本を検索して読む。

例:

- grep / ripgrep
- file search
- repository search
- DB query
- API search

向いている場面:

- 更新が速い
- 正本を直接検索できる
- 型番や識別子など正確な文字列が多い
- index同期を避けたい
- 検索経路を追跡したい

言い換えが非常に多い資料では、意味検索との比較が必要。

## SQL / 集計基盤

件数、合計、平均、割合、groupingなどは検索ではなくデータ処理として扱う。

LLMに自由なSQLを書かせる場合も、指標定義は固定する。

たとえば「売上」なら、対象期間、計上基準日、キャンセル、返金、税、通貨などを先に決める。

可能ならsemantic layerや定義済みqueryへ寄せ、LLMには定義を発明させない。

## 履歴管理

「いつから正しかったか」「当時何を知っていたか」を扱う場合は、検索indexではなく履歴をデータモデルとして持つ。

必要に応じて、事実が有効だった期間と、システムがその事実を認識していた期間を分ける。

詳細は data-lifecycle.md を参照する。

## 階層要約

全体傾向を繰り返し問う場合、あらかじめ要約の階層を作る。

原文
→ 文書単位の要約
→ グループ単位の要約
→ 全体要約

上位要約から結論を出し、必要に応じて下位の根拠へ降りる。

要約は元資料の代わりではないため、再生成条件と根拠への参照を持たせる。

## Hybrid / Router

実務では1方式ですべての質問を解かない方が自然なことが多い。

質問
→ ルーター
→ 探す: RAG
→ 数える: SQL
→ 時点を見る: 履歴DB
→ 全体を見る: 全件分析 / 要約

ルーターの分類も評価対象にする。

## 選択の目安

| 条件 | 第一候補 |
| --- | --- |
| 資料が少なく全体を読む必要がある | 全文投入 |
| 更新が速く正本を直接探せる | その場検索 |
| 言い換えが多く関連情報を探したい | RAG |
| 正確な件数・数値が必要 | SQL / 集計 |
| 過去時点の正しさが必要 | 履歴管理 |
| 全体傾向を頻繁に聞く | 階層要約 / 全件分析 |
| 複数種類の質問が混在する | Router + 複数方式 |

最終判断は質問、データ量、更新頻度を中心に、正確性、権限、コスト、応答時間を加えて行う。
