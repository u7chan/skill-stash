# 検索設計

この資料は「探す」質問にRAGを使うと決めた後に読む。

検索方式を先に高度化するのではなく、評価用の質問で失敗が確認できた箇所だけ改善する。

## 基本の流れ

代表的な流れは次のとおり。

質問
→ query rewrite / decomposition
→ キーワード検索 と 意味検索
→ 結果統合
→ reranking
→ 上位候補
→ LLM
→ 回答と根拠

すべての段を必須にしない。

## 文書分割

chunkは文字数だけで機械的に切るのではなく、意味上の境界を優先する。

候補:

- 見出し単位
- 段落単位
- セクション単位
- 1レコード / 1チケット / 1メッセージ単位
- コードなら関数、型、モジュール単位

### chunkに持たせる情報

断片だけでは意味が失われる場合、検索用テキストに文脈を足す。

例:

- 文書名
- セクション名
- 製品名
- 対象年度
- この断片が何の一部かを示す短い説明

回答時に表示する原文と、検索精度向上用の補助文脈は分けて持ってもよい。

## キーワード検索と意味検索

### キーワード検索が強い場面

- 型番
- エラーコード
- API名
- 固有名詞
- 決まった言い回し
- 正確な文字列

### 意味検索が強い場面

- 言い換えが多い
- 同じ概念を人ごとに違う表現で書く
- 質問と資料で使う語彙が異なる

どちらか一方に決め打ちせず、実データで比較する。

## ハイブリッド検索

キーワード検索と意味検索を並行して実行し、結果を統合する。

確認する。

- 片方でしか拾えない質問があるか
- 順位統合をどうするか
- 同一文書の重複をどう扱うか
- metadata filterをどこで適用するか

## メタデータによる絞り込み

検索対象を狭めるために使う。

例:

- tenant
- product
- document type
- language
- status
- date range
- access scope

filter後の候補数が不足していないか観測する。

結果が少ないままLLMへ渡すと、根拠不足でも回答だけ成立してしまうことがある。

## 再ランキング

初段検索で広めに候補を拾い、質問との関連性を別段で並べ直す。

特に次の場合に検討する。

- 検索上位に似ているだけの文書が多い
- ハイブリッド検索後の順位が不安定
- 必要な根拠は拾えているが上位に来ない

## 質問の書き換え・分解

ユーザーの質問を検索しやすい形へ変換する。

使いどころ:

- 会話文が長い
- 1質問に複数論点がある
- 代名詞が多い
- 略称と正式名称が混在する

元質問と変換後の検索語の対応を追跡できるようにする。

## Top-K

大きくすればよいとは限らない。

少なすぎると根拠を落とし、多すぎると関係の薄い文脈が増える。

評価セットで次を確認して決める。

- 必要な根拠がK件内に入るか
- 不要な文書が回答を乱さないか
- latency / token costが許容できるか

## 根拠の提示

回答だけでなく、利用した資料へ戻れるようにする。

最低限残したい情報:

- source id
- document title
- chunk id
- 元文書への参照先
- 版や更新日時
- 検索時の権限範囲

引用箇所と実際の主張が対応しているかも評価する。

## 改善の順序

1. 代表質問で失敗を再現する
2. 検索失敗か回答生成失敗かを分ける
3. 失敗した検索パターンを特定する
4. 最小の変更を入れる
5. 同じ評価セットで再計測する

失敗が確認できない状態でchunk、embedding、rerankerを一度に変更しない。
