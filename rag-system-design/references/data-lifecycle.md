# データの更新・履歴・インデックス運用

RAGは検索できるようになった時点では完成していない。

正本が変わったときに、検索結果も正しく変わり続ける仕組みまで設計する。

## 正本を決める

最初に何が正しいデータかを決める。

例:

- ファイルストレージ
- Git repository
- 業務DB
- SaaS
- 文書管理システム
- API

ベクトルストアや検索インデックスを正本にしない。

インデックスは再生成できる派生データとして扱う。

## 文書の識別

同じ文書を更新するのか、新しい文書として追加するのかを判定できるIDを持つ。

候補:

- source id
- document id
- source URI
- revision
- content hash

ファイル名だけに依存するとrenameや移動で重複を作りやすい。

## 更新

更新時に確認する。

- 旧chunkをどう特定するか
- 差分更新か全置換か
- 更新中に旧版と新版が混ざらないか
- 取り込み失敗時にどちらを有効にするか
- 更新完了をどう観測するか

## 削除

正本から消えたデータが検索indexに残り続けないようにする。

特に権限撤回、契約終了、個人情報削除では重要。

hard delete、tombstone、inactive flagなど方式は選べるが、検索結果へ出なくなることを確認できることが重要。

## 再インデックス

次の場合は再インデックスが必要になることがある。

- embedding model変更
- chunkingルール変更
- 検索用文脈の変更
- schema変更
- メタデータ追加
- analyzer / tokenizer変更

インデックスの版を持ち、新旧が混在していないか確認できるようにする。

## 更新反映の速さ

正本を更新してから検索へ反映されるまでを要件として持つ。

例:

- 即時
- 数分以内
- 1時間以内
- 日次

freshnessの要求が高い場合は、事前indexよりその場検索の方が単純なこともある。

## 時系列

日時メタデータを持つだけでは、履歴質問に十分とは限らない。

### 有効時間

その事実が現実世界でいつ有効だったか。

例: valid_from / valid_to

### 記録時間

システムがその事実をいつ知ったか。

例: recorded_from / recorded_to

後から訂正が入る業務では、この2種類がずれる。

「その時点で実際に有効だった条件」と「その時点で把握していた条件」の両方に答える必要があるなら、bi-temporalな扱いを検討する。

## 要約の更新

階層要約を使う場合、原文更新時にどの要約を再生成するか決める。

原文と要約の対応を追跡できないと、古い要約が残る。

## 最低限持ちたいメタデータ

必要なものだけ採用する。

- source_id
- document_id
- source_uri
- document_type
- created_at
- updated_at
- revision
- valid_from / valid_to
- ingested_at
- index_version
- content_hash
- access_scope

## 運用確認

本番導入前に最低限確認する。

- 追加した資料が検索できる
- 更新した旧内容が残らない
- 削除した資料が検索されない
- 権限変更が反映される
- 取り込み失敗を検知できる
- インデックスの版を確認できる
- 正本まで辿れる
- freshness要件を満たす
