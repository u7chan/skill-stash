# 評価

RAGの調整は、代表質問に対する再現可能な評価を作ってから行う。

検索と回答を分けて見る。

## 評価セット

実際の利用場面から質問を集める。

最初は小さくてよい。

| 項目 | 内容 |
| --- | --- |
| question | 実際の質問 |
| expected evidence | 必要な根拠 |
| expected behavior | 期待する回答・拒否・確認 |
| question type | 探す / 数える / 時点 / 全体 |
| failure risk | 間違えた場合の影響 |

簡単な質問だけでなく、似た文書、古い文書、該当なし、権限なしなども含める。

## Retrieval評価

まず、答えるために必要な根拠を検索できているかを見る。

確認する指標・観点:

- Recall@K
- Precision@K
- MRRなど順位の評価
- 必要な根拠が上位に入った割合
- exact matchが必要な質問の取りこぼし
- 言い換え質問の取りこぼし
- metadata filter後の候補不足
- 重複chunkの偏り

数値指標だけでなく、失敗パターンを分類する。

## 回答評価

検索で根拠を取得できても、回答が正しいとは限らない。

確認する。

- 正しさ
- 根拠への忠実さ
- 必要事項の網羅性
- 引用と主張の対応
- 根拠のない断定
- 分からない場合に答えを作らないか
- 質問に必要な条件を勝手に補っていないか

## 見つからない場合の評価

次を区別する。

- 本当に資料が存在しない
- 検索に失敗した
- 権限がなく見えない
- filterで候補が消えた
- indexが古い

これらを同じ「ありません」にしない。

区別できない場合は、断定の仕方を弱める。

## Router評価

複数方式へ振り分ける場合、ルーティング自体を評価する。

- 集計質問をRAGへ送っていないか
- 履歴質問を通常検索だけで答えていないか
- 混合質問を適切に分解できるか

## 回帰評価

変更前後で同じ質問セットを実行する。

対象:

- chunking
- embedding
- keyword analyzer
- fusion
- reranker
- prompt
- LLM
- metadata
- Top-K

1回の変更で複数要素を変えすぎない。

## 本番で見る指標

必要に応じて記録する。

- 検索結果0件率
- 平均候補数
- citation利用率
- 回答拒否率
- ユーザーの再質問率
- latency
- token usage
- retrieval / rerank cost
- index freshness
- ingest failure
- fallback発生率

## 完了条件

「精度が高い」ではなく、対象業務に合わせた合格条件を置く。

例:

- 重要質問では必要根拠がTop-Kに入る
- 集計質問はRAGへ流れない
- 根拠がない場合は断定しない
- 権限外文書は検索候補に入らない
- 更新後の許容時間内に新版へ切り替わる

完璧な単一スコアを作るより、重大な失敗を個別に防ぐ。
