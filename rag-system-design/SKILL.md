# RAG System Design

RAGを前提に設計を始めない。

最初に「利用者は何を知りたいのか」を確認し、その質問をRetrievalで答えるべきかを判断する。RAGは関連する情報を探すことには強いが、全件性、正確な集計、時系列、全体傾向まで同じ仕組みで解こうとすると、もっともらしい誤答を作りやすい。

目的は高機能なRAGを作ることではなく、質問とデータの性質に合った最小の仕組みを選ぶことである。

## 壁打ちの進め方

- 一度に質問を並べすぎず、原則として1問ずつ確認する。
- すでにユーザー、資料、コード、既存システムから分かることは聞き直さない。
- 技術選定より先に、利用目的と代表的な質問を確認する。
- 途中でRAGが不要だと分かったら、RAG設計を続けず別方式を提案する。
- 不明点を推測で埋めない。ただし設計を進められる範囲では仮定を明示して前へ進む。
- 特定のベクトルDB、LLM、クラウド、フレームワークを最初から前提にしない。

## 判断の順序

### 1. 利用目的を明確にする

まず、この仕組みで何を成立させたいのかを確認する。

最低限、次を把握する。

- 誰が使うか
- 何を知るために使うか
- どの資料・データを対象にするか
- 誤答したときの影響
- 回答に根拠や引用が必要か

実装方法ではなく、利用者の質問から始める。

### 2. 代表質問を集める

最初は3〜5問程度でよい。必要なら最終的に20問程度まで増やし、実際の利用場面を偏りなく表せる質問セットにする。

質問は言い換えず、できるだけ実際に利用者が入力する形で残す。

### 3. 質問を分類する

代表質問を次の4種類へ分類する。

- 探す: 関連する資料、記述、根拠、類似内容を見つけたい
- 数える: 件数、合計、平均、割合などを正確に求めたい
- 時点を見る: いつ変わったか、ある時点では何が正しかったかを知りたい
- 全体を見る: 全資料を踏まえた傾向、比較、総括を知りたい

1つの質問に複数の性質がある場合は分解する。

詳細な判定は references/question-routing.md を参照する。

### 4. データの性質を確認する

方式を決める前に、少なくとも次を確認する。

- データ量
- 1件あたりの大きさ
- 更新頻度
- 削除・訂正の頻度
- 構造化 / 非構造化
- 用語や言い回しの揺れ
- 正本がどこにあるか
- 最新性の要求
- 全件性や数値の正確性
- 過去時点への問い合わせ有無
- ユーザーごとの閲覧権限

### 5. RAGを含む候補を比較する

質問とデータに応じて、次から最も単純な方式を選ぶ。

- 全文をそのままLLMへ渡す
- ファイル・DB・APIをその場で検索する
- RAGで意味検索する
- SQLや集計基盤へ問い合わせる
- 履歴・時点管理されたデータへ問い合わせる
- 階層要約または全件読み込みを使う
- 質問ルーターで複数方式を使い分ける

比較基準は references/alternatives-to-rag.md を参照する。

### 6. RAGが必要な部分だけ検索設計を詰める

RAGを使うと決めた質問だけ、次を設計する。

- 文書の分割単位
- chunkに持たせる文脈
- キーワード検索と意味検索の併用
- metadata filter
- 検索結果の統合
- reranking
- Top-K
- query rewrite / query decomposition
- 回答根拠と参照元の提示

詳細は references/retrieval-design.md を参照する。

Top-Kやchunk sizeに万能な固定値を置かない。評価用の質問セットを使って決める。

### 7. 更新・履歴・権限を設計する

検索精度だけで終わらせない。

- 文書更新時の再取り込み
- 削除の反映
- indexの古さ
- 再index条件
- 過去時点の扱い
- 権限変更の反映
- 正本との対応
- 回答根拠の追跡

更新と履歴は references/data-lifecycle.md、権限と安全性は references/security-governance.md を参照する。

### 8. 評価方法を先に決める

本番データを増やす前に、代表質問から小さな評価セットを作る。

Retrievalと回答生成を分けて評価する。

詳細は references/evaluation.md を参照する。

「前より良さそう」「モデルを変えたら賢くなった」で完了にしない。

## 方式を決める3つの軸

迷ったら次の3つに戻る。

1. 質問の型: 探索 / 集計 / 時系列 / 全体分析
2. データ量: 必要な資料をそのまま読ませられるか
3. 更新頻度: indexを維持する価値があるか

必要に応じて正確性、権限、コスト、応答時間を追加する。

## Guardrails

避ける。

- RAG導入を結論にしてから要件を集める
- ベクトルDBやembedding modelの選定から始める
- Top-K検索を全件取得として扱う
- RAGの検索結果だけで正確な件数や合計を出す
- 類似度だけで新旧や有効期間を判断する
- 数件の検索結果から全体傾向を断定する
- metadata filterだけで履歴モデルの代わりにする
- 検索精度だけを評価し、最終回答を評価しない
- 回答後に権限チェックすればよいと考える
- 更新、削除、権限変更、再indexを運用設計から外す
- chunk size、overlap、Top-Kなどを根拠なく固定値にする
- RAGを使わない方が単純なケースでも構成を複雑にする
