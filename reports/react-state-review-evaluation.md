# react-state-review の評価レポート

実施日: 2026-10-29

## 判断

**スキルの採用はいったん保留し、検証結果だけを残す。** [追加案のPR #46](https://github.com/u7chan/skill-stash/pull/46) の文書設計は妥当だったが、今回の適用比較では、スキルを使うことで判断品質が高まるという結果は得られなかった。

スキル版は短時間で完了した一方、基準版が検出した非同期応答の競合を見落とし、Reducer移行案の改善効果にも根拠不足があった。ただし、これは単一ペアの部分調査であり、スキル一般の欠陥やモデル一般の能力差を示すものではない。

また、**useReducer自体を不適切・不要と判断したわけではない。** 連動する状態遷移を集約し、重要な規則を独立してテストできるなら導入価値はある。今回の競合には、まず応答対象・世代の確認という最小修正が必要であり、それとReducer化の要否は別問題である。

## 判断内容の比較

### 非同期応答の対象取り違えは基準版だけが検出

[EnvVarsTab.tsx:199–219](https://github.com/u7chan/monorepo/blob/f74a8cb4341c09fc4054f3e1ed69f575166ce6ce/projects/u7agent/client/src/components/EnvVarsTab.tsx#L199-L219) は、未取得の変数Aの詳細を待った後、現在の編集対象を確認せず `setValue` と `setBusy(false)` を呼ぶ。同じmount内で別の行Bを開くと、Aの古い応答がBの下書きを更新できる。

- 基準版はこの経路と、対象・世代ガードによる最小対策を挙げた。
- スキル版は同じ関数を通読したが、この競合を挙げなかった。提案する `prefetched(value)` にも応答対象や世代のpayload・照合条件がなく、その案だけでは競合を解消しない。
- 親の検証では正本の `openEdit` 本体を抽出し、Promiseを保留して「Aを待つ→Bを開く→Aの応答を返す」の順で実行した。Bの下書きがAの値になることを確認した。
- 行メニューと閉じる操作がbusyで無効化されないことも確認した。[親のscope key](https://github.com/u7chan/monorepo/blob/f74a8cb4341c09fc4054f3e1ed69f575166ce6ce/projects/u7agent/client/src/components/SessionFilesPanel.tsx#L193-L195) は会話切替に効くが、同じmount内のA→B切替を防がない。

これはソース抽出ハーネスと呼出し経路による検証であり、React・DOM・ブラウザでの再現ではない。対象アプリは修正しておらず、別Issueも起票していない。

### スキル版の改善主張と提案が一致しない

スキル版は、先読み中の保存無効化を「Enter送信が無言で捨てられる」「保存操作の取りこぼし」の根拠にした。しかし、[submit guard](https://github.com/u7chan/monorepo/blob/f74a8cb4341c09fc4054f3e1ed69f575166ce6ce/projects/u7agent/client/src/components/EnvVarsTab.tsx#L222-L224) と [disabled button](https://github.com/u7chan/monorepo/blob/f74a8cb4341c09fc4054f3e1ed69f575166ce6ce/projects/u7agent/client/src/components/EnvVarsTab.tsx#L482-L485) があり、取得中の保存を許すという仕様は確認されていない。この経路だけでは不具合と断定できない。

さらに、提案でも「`prefetching` 中は `saveStarted` を無視する」としながら、「取りこぼしが型で作れなくなる」と説明していた。取得状態を表示しやすくする効果はあっても、保存操作について挙げた問題が解消する説明にはなっていない。

`closeForm` と保存成功時の下書きリセット重複は実在する。ただし、feedbackの寿命を分けたreset helperや、まとまった `useState` で足りるかの比較がなかった。移行価値をすべて否定するのではなく、推奨の強さが根拠を超えていると評価した。

### FileBrowserの連動更新は基準版だけが深掘り

基準版は [FileBrowser.tsx:346–382](https://github.com/u7chan/monorepo/blob/f74a8cb4341c09fc4054f3e1ed69f575166ce6ce/projects/u7agent/client/src/components/FileBrowser.tsx#L346-L382) の削除・rename時の連動更新と、[閉タブ後のcleanup](https://github.com/u7chan/monorepo/blob/f74a8cb4341c09fc4054f3e1ed69f575166ce6ce/projects/u7agent/client/src/components/FileBrowser.tsx#L416-L429) を追い、既存純関数を合成する案と回帰検証を示した。これはユーザー可視の既知不具合ではなく、連動遷移と後追い同期を集約する候補として妥当だった。

スキル版はこのファイルを深掘りしていない。候補選択の差なので、未調査そのものを文書の欠陥とはしない。ただし短縮時間には調査範囲差が含まれる。なお、基準版の保存に関する説明も、memory snapshotとvalidationを通るlocalStorage保存を区別して読む必要があり、無条件には正解と扱わない。

### 両条件でできた判断

- `useSessions` や `App` の大きさ・state数だけで全面Reducer化しない。
- `App` のdesktop/mobile、dialog key、退場アニメの契約を維持する。
- 非同期処理や独立した一覧状態を巨大Reducerへ入れない。
- ブラウザ未検証と調査範囲の制約を明記する。

スキル版は `SpeechPlayground` の `null = 保存値へ追随` という意味も保った。一方、「client/srcのTS/TSX全581ファイル」という冒頭の記述は誤りで、確認時のsrcは365、testは215ファイルだった。初期一覧がclient全体を対象としていたことと混同していた。

## 静的レビューと検証の限界

スキル本文のreadonly default、代替案優先、状態数だけで判断しない方針、batchingの考慮、Reducerの純粋性、State/Action/境界/回帰リスクを求める構成は妥当だった。frontmatterとREADMEリンクも確認した。[文書差分への必須指摘なしとして投稿したレビュー](https://github.com/u7chan/skill-stash/pull/46#pullrequestreview-5692429792) は、実地の性能保証を意味しない。

本文は既に具体的経路・最小代替比較・Reducerだけで不正状態が消えるわけではないことを要求している。今回の指示不遵守を、そのまま文書の欠陥とは認定しない。

親は対象コードの既存テスト12ファイルを読み取り専用で実行し、**224件成功・失敗0件**を確認した。子はこれらを実行していない。全体の `pnpm check`、GUI、実ブラウザは未実施である。終了時に対象clientと関連規約が固定コミットから変わっていないことも確認した。

このレポートには判断・比較条件・主要な検証経路を残す。セッション生ログ、生成レポート全文、ローカル絶対パス、検証ハーネスは収録していないため、元セッションの全計測値をこのファイルだけから再集計できるわけではない。

## 再評価するなら

1. 移行推奨の前に、既存のguard・disabled・keyで問題を説明・防止できないか反証する。
2. 提案後に同じイベント列を流し、何が変わるかを確認する。非同期では「取得開始→別対象へ移動→旧応答」を追い、対象ID・世代ガードの要否を判断する。
3. reset helperやオブジェクトstateとの比較を終えてから移行を推奨する。
4. 連動更新の正例、既存保存ガードの負例、古い非同期応答の競合例を小さなfixtureにし、複数の独立実行で比較する。

今回は評価記録だけを追加し、スキルの導入・修正や対象アプリの変更は行わない。
