# Security Incident Audit 報告テンプレート

**判明した事実だけを記録する。** 影響・原因・責任者を推測で埋めず、`不明`、`未確認`、`未決定` を明記する。生ログ・個人情報・認証情報は報告本文に貼らず、アクセス制御された証拠保存先の参照を使う。

## 1. 緊急報告（他の項目より先に送る）

- 異常候補: `あり` / `確認範囲内で検知なし` / `未確認`。候補の検出条件・比較基準・誤検知可能性:
- 強い侵害兆候（あれば）・発見日時・タイムゾーン・証拠参照:
- 異常候補のエスカレーション日時・連絡先・確認状態:
- 人間によるインシデント宣言: `未判断` / `宣言` / `否定`、判断担当者・日時・根拠・チケット参照:
- 緊急連絡経路と独立性（疑われるIdP/メール/チャット等は使用しない）:
- 漏えいの可能性: `あり` / `不明`（専門調査で判断）
- ログ消失リスク: 対象・失効予定日時・保全の推奨期限・依頼先・承認状態
- 緊急のパッチ適用等: 対象・理由・影響・承認待ち操作
- ここに「確認範囲内で検知なし」と記載しても、未点検・ログ欠損の領域が安全になったことを意味しない。

**異常候補の段階で速やかにエスカレーション**するが、AIが一律にインシデント宣言しない。重大な兆候は判定待ちでも緊急連絡し、人間の対応責任者がトリアージして宣言／否定の理由を記録する。連絡経路が侵害疑いの場合は独立した代替経路へ切り替える。

## 2. 実行条件・情報源

- 点検日時とタイムゾーン、組織・部署・環境・許可された範囲:
- エージェント実行先、外部AI/ツールへの送信許可、扱えるログの機密区分、マスキング方針:
- 使用した読み取り専用資格情報の識別子（秘密値は記載しない）、確認した権限:
- 書き込み権限しかなく調査を止めた範囲:
- IPA原文の確認日時・確認時点の更新日・差分、適用可否の人間の承認者・日時・承認チケット参照（未承認なら適用しない）:
- 参照したJPCERT/CC・行政機関・ベンダーの注意喚起と取得日時:
- 最新情報を確認できない情報源（あれば）:

## 3. 棚卸しの照合記録

| 情報源 | 対象部署/範囲 | 件数または識別子 | 照合結果・不一致 | 未確認理由・次の担当者 |
| --- | --- | --- | --- | --- |
| IdP / SSOアプリ一覧 | ... | ... | ... | ... |
| 請求・購買・経費 | ... | ... | ... | ... |
| DNS / クラウド資産 / 公開設定 | ... | ... | ... | ... |

単一の情報源のみで棚卸しの網羅性が担保できない場合は未確認を明記する。未承認の範囲を資産一覧から黙って除かない。

## 4. 資産別点検結果

| 資産/部署 | ログ 1か月→3か月（確認した期間/保持期限） | アカウント | パッチ | **保有データ** | 判定 | 責任者 |
| --- | --- | --- | --- | --- | --- | --- |
| ... | 1か月: ... / 3か月: ... | ... | ... | ... | ... | ... |

各資産について次も記録する。

- 公開区分・利用サービス・所有部署・構成要素・テナント:
- ログ: 実際に確認した期間・タイムゾーン・欠損・保持期限・利用者/提供者の参照可能範囲・証拠参照・`未取得/取得不能/運用開始前（証明済み）` の区分と理由コード・稼働開始の管理面証跡:
- アカウント: 照合元・変更監査ログ・確認結果・証拠参照:
- パッチ: 管理主体・バージョン・未適用修正・対応期限・証拠参照。SaaSの提供者管理なら `非適用（提供者管理）` と記録する:
- **保有データ: 種類・保存先・管理主体・アクセス権・保存必要性・不要な保有の有無・証拠参照**（データなしの場合も根拠）:
- 必要な承認・引継ぎ・次の点検日時:

### 状態と集約（ロールアップ）の規則

- **個別項目**: `確認済み` / `要対応` / `未確認` / `非適用（根拠・管理主体）`。
- **資産全体**: `要対応` / `未確認` / `確認済み` / `対象外`。
- `要対応`: 異常が確認された、緊急の保全や未適用修正など対応事項がある場合。未確認も残る場合は両方を記録する。
- `未確認`: 必須の棚卸し、ログ（直近1か月**と**その後3か月）、アカウント、パッチ、保有データのいずれかに未確認がある、または実行前の情報持ち込み・権限条件が満たせない場合。未確認ログは理由コードで **`NOT_CHECKED`（未実施）/ `ACCESS_DENIED`（権限）/ `RETENTION_EXPIRED`（保存期間経過）/ `COLLECTION_GAP`（収集欠損）/ `START_DATE_UNVERIFIED`（稼働開始未証明）** を区別する。単に確認していない場合と取得不能を混同しない。
- **例外**: 稼働3か月未満をクラウド/SaaSの管理面の作成時刻・監査証跡等で証明し、全稼働期間を確認した場合は、稼働開始前の期間を `PRE_OPERATION_VERIFIED` として欠損に含めない。自己申告のみでは認めない。
- **永久未確認を避ける運用**: 取得不能な過去ログを自動で再取得し続けない。残存リスクの受容・保存期間改善・再点検期日を人間の承認チケットで管理する。リスク受容は「ログを確認した」ことにはならず、当該期間は `未確認（取得不能）` のまま明示する。改善後に3か月分の実ログが蓄積された時点で再判定する。
- `確認済み`: 必須項目がすべて根拠付きで確認済み/根拠付き非適用、かつ未確認・要対応が**ない**場合のみ。侵害が存在しない保証ではない。
- `対象外`: **資産全体を点検対象から除く**こと。理由・範囲・証拠・承認者・承認日時に加え、**検証可能な承認チケットID/URL等への参照**とその内容確認が必須。文字列だけ・未確認の参照では認めず `未確認` とする。
- `非適用`: 資産内の個別項目でのみ使用し、管理責任の所在と理由を付ける。SaaSの提供者管理パッチは `非適用（提供者管理）` であり、資産全体の `対象外` ではない。
- 資産に `要対応` と `未確認` が両方あれば、資産の主判定は `要対応` とし、未確認項目を消さない。
- 棚卸しの情報源自体が不足する場合、**報告全体も点検未完了**。個別資産の `確認済み` をもって組織全体の安全を宣言しない。
- IPAの最新改訂や関連機関の情報を確認できなかった場合、**最新情報未確認として暫定報告**にする。確認した時点と不足する情報源を明記する。

## 5. 異常・指摘事項（IDごと）

- ID / 対象資産 / 重大度（未確定なら不明）:
- **観測した事実**・発見時刻・証拠参照・確認できた期間:
- 異常候補の連絡先・連絡日時・トリアージ状態（担当者未定なら割当依頼中）:
- インシデント宣言の有無・判断担当者・日時・判断根拠・検証可能なチケット参照:
- 現状の影響・漏えい範囲（不明可）:
- **仮説**・正常要因の検討（引継ぎ後、検討担当者・判断根拠を明記）:
- 次の作業 / 承認要否 / 期限（未決定可）:

## 6. 未確認・制約

- 対象 / 区分（未取得・取得不能・運用開始前） / 理由コード（`NOT_CHECKED / ACCESS_DENIED / RETENTION_EXPIRED / COLLECTION_GAP / START_DATE_UNVERIFIED / PRE_OPERATION_VERIFIED`） / 対象期間 / 根拠（ログ欠損・保持不足・権限不足・AI入力未承認・棚卸し未突合・最新情報未取得など）
- 残るリスク / 必要な追加調査 / 調査担当者（未決定可） / 実施期限

## 7. 改善提案と証拠一覧

- 改善: 公開範囲、MFA、権限、パッチ、ログ収集/保持、データの必要最小化
- 証拠: ID / 取得元 / 取得日時・タイムゾーン / 検索条件 / 保存先 / 取扱制限
- 報告状態: `点検完了（確認範囲明記）` / `暫定報告・点検未完了`。ログ取得不能の承認済みリスク受容は別記し、点検完了・安全宣言とは区別する。

異常候補・強い侵害兆候のエスカレーションと失効間近のログの保全依頼は、総合報告を完成させる前に実施する。連絡先が侵害疑いの基盤上にある場合は送信せず、独立した経路を確認する。
