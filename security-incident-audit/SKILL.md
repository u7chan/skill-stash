# 不正アクセス緊急点検

対象組織の管理権限内で、不正アクセス・情報漏えいの兆候を点検する。調査項目は `references/checklist.md`、出力形式は `references/report.md` を参照する。

## 原則

- **読み取り専用で開始する。** 設定変更、パッチ適用、アカウント停止、秘密情報のローテーション、能動的スキャン、対外通知は、影響と手順を提示して明示的な承認を得る。緊急時も組織の承認済み対応手順に従う。
- **許可された環境・テナントのみ調べる。** 権限外の部署や外部サービスは、調査方法と担当者を特定し「未確認」とする。
- **確認できないことを安全と判断しない。** ログ欠損・権限不足・基準値不明を明示し、異常なしと区別する。
- **証拠を保護する。** 取得元、対象、時刻・タイムゾーン、期間、実施者、検索条件、結果を残す。生ログや個人情報・トークンは必要最小限に扱い、原本は変更しない。外部AIサービスへ機密ログを無断送信しない。
- **侵害を断定しない。** 異常はインシデント対応の対象として速やかに報告し、侵害の有無や影響範囲は専門的な調査で判断する。

## 実施手順

1. **範囲と権限を確定する**
   - 組織・部署・環境・対象期間・参照可能な管理画面/ログ・連絡先を確認する。
   - 不足情報があっても、許可済み範囲の棚卸しと点検を先行する。
2. **対象資産を列挙する**
   - 自組織の外部公開アプリ/API/管理画面と、利用中のクラウド・SaaS・VPN・認証基盤を部署単位まで洗い出す。
   - 所有者、公開経路、認証方式、構成要素、機密データ、ログ保管場所、保持期間、参照権限を一覧化する。
3. **ログを調べる**
   - まず直近1か月の取得可能なログを調べ、兆候・欠損・リスクに応じて3か月等へ段階的に広げる。
   - エラー/認証失敗の量、送信元IP、時刻、成功ログイン、権限変更、大量アクセス・取得などを平時と比較する。
   - 季節性・営業時間・メンテナンス・既知の監視アクセスを考慮し、異常の根拠を記録する。閾値は根拠なく固定しない。
4. **アカウント・権限を照合する**
   - 承認済みの台帳やIdPと照合し、未承認の新規アカウント、無効化済みアカウントの再有効化、不審な特権付与を確認する。
   - 可能なら作成・変更操作の監査ログまで追跡する。
5. **脆弱性と保有データを点検する**
   - OS、ミドルウェア、依存パッケージ、コンテナ、ネットワーク機器、外部連携を対象に、既知の未適用修正と公開状況を整理する。
   - 重要度・悪用状況・影響に基づいて早急な適用を提案するが、変更は承認後に行う。
   - 保有データの種類・保存場所・アクセス権・保存必要性も確認する。
6. **判定・エスカレーションする**
   - 異常なログやアカウントを発見した場合、速やかにインシデント対応フローへ引き継ぐ。漏えい可能性を考慮し、専門ベンダーによる調査を推奨する。
   - 証跡の保全を優先し、独断でログ削除・再起動・侵害端末の初期化を行わない。
7. **結果を報告する**
   - `references/report.md` に従い、対象・実施済み・異常・未確認・緊急対応・担当者を区別して出力する。
   - 調査後の改善候補（MFA、公開範囲、最小権限、ログ取得/保持、データ最小化）を添える。

## 完了条件

- 対象資産ごとに「確認済み／要対応／未確認／対象外」のいずれかが付いている。
- 全ての異常に証拠、仮説、影響、次の担当者が紐づいている。
- 未確認理由、ログ保管の制約、承認待ち操作が明示されている。
- インシデントの疑いを「問題なし」に丸めず、緊急報告事項として先頭に示している。
