# Frontier Harness Diagnosis

高性能なフロンティアモデルを、古いモデル向けの過剰なハーネスで縛っていないか診断する。

目的は指示を減らすこと自体ではない。モデルが一般能力で判断できる部分は任せ、リポジトリ固有の制約、安全境界、完了条件、必要な文脈だけを残すことで、正確性を保ちながらコンテキスト消費・不要なツール実行・停止回数を減らす。

## 基本原則

- モデルを細かく操縦するより、目的・制約・境界・完了条件を明確にする。
- 常時読む情報と、必要なときだけ読む情報を分ける。
- Skillのdescriptionは説明文ではなく、発火条件として評価する。
- Skill本体は必要に応じてReferenceへ振り分ける入口として薄く保つ。
- 一般的な開発常識を重複して教えず、リポジトリ固有の判断材料を優先する。
- 安全なローカル作業まで逐次承認にしない。一方で破壊操作や本番操作の境界は弱めない。
- モデル固有の傾向を、すべてのフロンティアモデルに共通する性質として決めつけない。

## 診断対象

対象になり得るものを確認する。

- `AGENTS.md`、`CLAUDE.md` などの常時指示
- Skillのdescriptionと`SKILL.md`
- `references/` や設計ドキュメントへの参照方法
- タスクプロンプトやIssue実装プロンプト
- Permission / approval / stop条件
- テスト・lint・検証の強制ルール
- Done条件
- ツール利用順序や固定workflow
- モデル別の例外ルール

対象が明示されていなければ、まずハーネス構成を確認し、診断に必要なファイルだけ読む。

## 診断の進め方

### 1. 指示を役割ごとに分類する

各ルールを次へ分類する。

- **Invariant**: 常に守るべきリポジトリ固有ルール
- **Conditional context**: 特定タスクのときだけ必要な情報
- **Safety boundary**: 破壊操作、本番操作、秘密情報などの停止境界
- **Done condition**: 完了を判断する条件
- **Model compensation**: 過去モデルの弱点を補うために追加された手順や注意

分類できないルールは、その存在理由を確認する。

### 2. 過剰制御を診断する

次の観点で確認する。詳細は `references/diagnostic-criteria.md` を参照する。

1. Skill発火条件
2. Progressive disclosure
3. 手順の細かさ
4. AGENTS.mdなどの常時コンテキスト
5. テスト・検証方針
6. Permissionと停止条件
7. Done条件
8. ツール・workflow固定
9. 重複指示
10. モデル固有ルールの混在

### 3. 削除ではなく最小改善を考える

問題を見つけても、すぐにルールを消さない。

まず次を判断する。

- 完全に削除できるか
- 条件付き参照へ移せるか
- 手順から制約・Done条件へ変換できるか
- 安全境界として残すべきか
- モデル固有補正として分離すべきか

代表的な改善パターンは `references/improvement-patterns.md` を参照する。

### 4. モデル差を分離する

フロンティアモデル全般に適用できる原則と、特定モデルでだけ観測された挙動を分ける。

モデル名やバージョンが指定されている場合でも、一般原則をモデル固有ルールに埋め込まない。

モデル差の扱いは `references/model-calibration.md` を参照する。

### 5. 改善前後を評価できる形にする

改善案は「短くなった」だけで評価しない。

最低限、次を比較できるようにする。

- タスク成功率
- 不要な確認・停止回数
- 不要なファイル読み込み
- 不要なツール実行
- コンテキスト消費
- テスト不足・過剰テスト
- リポジトリ固有ルールの遵守

評価方法は `references/evaluation.md` を参照する。

## 出力形式

### 総評

ハーネスが次のどこにあるかを短く示す。

- 適正
- やや過剰
- 過剰制御
- 情報不足 / 境界不足

### 診断結果

| 重要度 | 観点 | 現状 | 問題 | 改善案 |
| --- | --- | --- | --- | --- |
| High / Medium / Low |  |  |  |  |

重要度は、品質・安全性・コスト・停止頻度への影響で決める。

### 残すべきもの

削除・簡略化してはいけないリポジトリ固有ルール、安全境界、品質ゲートを明示する。

### 最小改善案

効果が高く変更量が小さい順に、原則3件以内で提案する。

必要なら変更対象ファイルと変更方針まで示すが、ユーザーが実装を求めていない限り勝手に修正しない。

### モデル固有の調整

モデル差が診断に影響する場合だけ記載する。根拠がないモデル特性は推測しない。

### 検証方法

改善前後で同じ代表タスクを実行し、何を比較すべきかを示す。

## 避けること

- 指示量が多いという理由だけで削除する
- 安全境界や必須品質ゲートまで「モデルが賢いから」で弱める
- Skill本体で全Referenceを常時読むよう要求する
- 一般的なベストプラクティスを大量に追加して逆にハーネスを肥大化させる
- 特定モデルで見られた挙動を全モデル共通として固定する
- トークン削減だけを成功指標にする
- 問題がない部分まで全面的に書き換える
