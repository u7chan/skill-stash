# 評価方法

ハーネス改善は、短文化やトークン削減だけで成功と判断しない。

## 代表タスクを固定する

改善前後で同じ種類のタスクを使う。

例:

- 小さなtypo修正
- 単一ファイルの機能変更
- 複数ファイルにまたがる実装
- schemaやAPI契約の変更
- 既存失敗テストの切り分け
- 破壊操作を含む依頼

最低でも「簡単なタスク」「通常タスク」「境界確認が必要なタスク」を含める。

## 比較する指標

### 品質

- 要求を満たしたか
- リポジトリ固有ルールを守ったか
- 必要なテストを行ったか
- 不要な変更を増やしていないか

### 自律性

- 不要な確認回数
- 不要な途中停止
- failureから修正・再検証まで継続できたか

### コンテキスト

- 常時読み込んだファイル数
- タスクに無関係なReference読込数
- prompt / instructionの概算量
- compactionやcontext上限への到達有無

### ツール利用

- 不要なツール実行回数
- 同じ情報の再取得回数
- 固定workflowのためだけに発生した操作

### 検証

- 必要な検証の不足
- 変更に対して過剰な検証
- failureを今回の変更起因か切り分けられたか

## 改善の判定

改善後は、少なくとも次を満たすことを目指す。

1. 成功率や品質を落とさない
2. 安全境界を弱めない
3. 不要なコンテキストか不要な操作を減らす
4. 不要な確認・停止を減らす
5. モデル変更時の補正箇所を局所化する

1つでも重大な品質劣化がある場合、単純なトークン削減を理由に採用しない。

## 変更は一度に増やしすぎない

複数の改善を同時に適用すると、何が効いたか分からなくなる。

優先順位の高い1〜3件を先に変え、代表タスクで比較する。効果が確認できたら次へ進む。

## モデル更新時

モデルを更新したら、古い補正ルールを自動的に引き継がない。

代表タスクで再評価し、不要になった補正は削除または無効化する。共通のリポジトリ制約と安全境界は、モデル更新を理由に変更しない。
