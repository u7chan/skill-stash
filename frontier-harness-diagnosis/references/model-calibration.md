# モデル差の扱い

フロンティアモデル向けハーネス設計では、一般原則とモデル固有の補正を分ける。

## 一般原則として扱いやすいもの

次は特定ベンダーや特定モデルに限定せず、強いモデルほど有効になりやすい設計原則として扱う。

- 常時コンテキストを必要最小限にする
- 必要な情報を段階的に読む
- 一般常識ではなくリポジトリ固有情報を優先する
- 手順よりGoal / Constraints / Boundary / Doneを明確にする
- Skillのdescriptionを発火条件として設計する
- 安全境界と品質ゲートは明示的に保つ
- 改善効果を代表タスクで検証する

ただし、これらも無条件に適用しない。タスク再現性、安全性、規制、監査などの理由で固定手順が必要なら残す。

## モデル固有として扱うもの

次のような性質はモデルごとに差が出やすいため、一般原則へ直接埋め込まない。

- 途中でユーザー確認へ戻りやすい / 戻りにくい
- 自発的にテストする / しない
- 長いSkill descriptionのルーティング精度
- 大量コンテキスト下での指示追従低下
- ツールを過剰利用する / 利用不足になる
- 失敗後の自己修正をどこまで継続するか
- Permissionを保守的に解釈する度合い

これらはモデル名、バージョン、thinking設定、実行ハーネスによって変わり得る。

## 補正ルールを追加する条件

モデル固有ルールは、次のいずれかを満たす場合だけ追加する。

1. 公式仕様や明確な契約がある
2. 同一条件の複数タスクで再現している
3. 既存ハーネスでは実害があり、補正で改善したことを比較できる

単発の失敗だけで恒久ルールを追加しない。

## 補正ルールの置き場所

可能なら共通ハーネスから分離する。

```text
common harness
  - repository invariants
  - safety boundaries
  - done conditions
  - conditional routing

model calibration
  - model-specific stop behavior
  - tool-use tendency
  - validation tendency
```

モデルを切り替えたとき、共通部分を壊さず補正だけ交換できる状態を目指す。

## 診断時の問い

モデル固有らしいルールを見つけたら確認する。

- この指示はリポジトリ要件か、モデルの弱点対策か
- 他のフロンティアモデルでも必要か
- 現在のモデルでもまだ必要か
- 削除した場合の失敗を再現できるか
- 共通ルールではなく補正層へ移せないか

## 過学習を避ける

ハーネスを1モデルに最適化しすぎると、モデル更新や切り替えのたびに古い補正が負債になる。

フロンティアモデル向けの基本方針は、**共通ハーネスを薄く安定させ、必要なモデル差だけ局所的に補正する**ことである。
