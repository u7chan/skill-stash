# Issue PR Orchestrator

Issue `#{issue}` の実装からPRレビュー完了までを管理する。オーケストレーター自身は原則として実装せず、各ロールへ作業を委譲する。

## 必須条件

作業開始前に次を確認する。

- 対象のIssue番号
- `impl` に使用するエージェント
- `review` に使用するエージェント
- `pr-fix` に使用するエージェント

3つのエージェントがユーザーから指定されていない場合は、勝手に選択せず、作業開始前に不足している指定を確認する。

## Roles

| Pane | Role |
| --- | --- |
| 1 | `impl` |
| 2 | `review` |
| 3 | `pr-fix` |

各ペインに割り当てるエージェントはユーザーの指定に従う。エージェント同士が暗黙に情報を共有していると仮定せず、オーケストレーターが必要な情報を明示的に引き渡す。

## Orchestrator

オーケストレーターは次を担当する。

- Issueの内容を確認する
- 作業ブランチを作成する
- 各ロールへ作業を指示する
- 各ペインの状態を管理する
- PR番号、レビュー結果、指摘内容を次工程へ渡す
- 次工程へ進めるか判定する
- `review` → `pr-fix` → `review` のループを管理する
- 完了条件を確認する
- 不要になったペインを終了する

原則として自分で実装しない。実装は `impl` または `pr-fix` に委譲する。

ただし、レビュー終盤に残った次のような低リスクかつ単純な修正だけは、自分で対応してよい。

- typo
- コメント修正
- import整理
- formatter適用
- lint修正
- 動作や設計に影響しない明らかな軽微修正

判断に迷う場合は `pr-fix` に委譲する。

## Initial Setup

次の順序で開始する。

1. Issue `#{issue}` の内容を確認する。
2. `impl` / `review` / `pr-fix` に使用するエージェントの指定を確認する。
3. 作業ブランチを作成する。
4. `impl` / `review` / `pr-fix` の3ペインを起動する。
5. 各ペインへ対応するロール、Issue番号、作業ルールを伝える。
6. `impl` にIssueの実装を開始させる。

`review` と `pr-fix` は、オーケストレーターから指示が来るまで待機させる。

## impl

Issue `#{issue}` を実装する担当。

### Responsibilities

- Issueの内容を確認する
- 必要な実装を行う
- 必要なテスト・検証を行う
- 変更をコミットする
- Pushする
- Draft PRを作成する
- PR番号をオーケストレーターへ返す

PR作成まで完了したら役割を終了する。オーケストレーターから終了指示を受けたらペインを終了する。

## review

PRをレビューする担当。オーケストレーターからPR番号を受け取るまで待機する。

### Responsibilities

PR番号を受け取ったら次を実施する。

- PRの変更内容を確認する
- Issueの要求を満たしているか確認する
- コードレビューを行う
- 必要に応じてテスト・検証結果を確認する
- 修正が必要な箇所はGitHub PRへ具体的なレビューコメントを書く
- レビュー結果をオーケストレーターへ返す

### Review Result

レビュー結果は、次のどちらかとして明確に返す。

#### 修正あり

- GitHub PRへ指摘コメントを投稿する
- オーケストレーターへ修正が必要であることを報告する

指摘コメントには可能な限り、問題となる箇所、問題である理由、期待する状態を含める。

#### 修正なし

追加修正が不要であることを確認したら、GitHub PRへ `LGTM` とコメントする。Approve操作は行わない。LGTM投稿後、オーケストレーターへレビュー完了を報告する。

## pr-fix

PRレビュー指摘への対応担当。オーケストレーターから修正指示を受けるまで待機する。

### Responsibilities

レビュー指摘を受け取ったら次を実施する。

- PR上のレビューコメントを確認する
- 指摘内容を修正する
- 必要なテスト・検証を行う
- コミットする
- Pushする
- 必要に応じてレビューコメントへ返信する
- 対応結果をオーケストレーターへ返す

修正完了後は、次の指示が来るまで待機する。

## Workflow

### 1. Implementation

1. オーケストレーターが作業ブランチを作成する。
2. `impl` にIssue実装を依頼する。
3. `impl` が実装・テスト・コミット・Pushを行う。
4. `impl` がDraft PRを作成する。
5. `impl` がPR番号をオーケストレーターへ返す。
6. オーケストレーターがPR番号を記録する。
7. `impl` ペインを終了する。

### 2. Review

1. オーケストレーターが `review` にPR番号を渡す。
2. `review` がPRをレビューする。
3. `review` が結果をGitHubとオーケストレーターへ返す。

修正指摘がなければ、`review` はPRへ `LGTM` コメントを投稿する。その時点でレビュー完了とする。

### 3. Review Fix Loop

レビュー指摘がある場合は次を実施する。

1. オーケストレーターが指摘内容とPR番号を `pr-fix` に渡す。
2. `pr-fix` が修正する。
3. `pr-fix` がコミット・Pushする。
4. `pr-fix` が対応結果をオーケストレーターへ返す。
5. オーケストレーターが `review` に再レビューを依頼する。
6. `review` が再レビューする。

追加指摘があれば同じループを繰り返す。レビュー → 修正 → 再レビューのループは最大3回までとする。3回実施しても解消しない場合は勝手に継続せず、状況、未解決事項、考えられる原因を整理してユーザーへ報告する。

## PR Comment Policy

レビュー担当は、修正が必要な場合のみ具体的な指摘をPRへ投稿する。指摘コメントには可能な限り次を含める。

- 問題となる箇所
- 問題である理由
- 期待する状態

`pr-fix` は必要に応じて指摘コメントへ返信する。修正済みで、再レビューでも問題がないことを確認したConversationはResolveする。

最終レビューで問題がなければ、`review` はPRへ `LGTM` コメントを投稿する。GitHubのApprove操作は使用しない。

## State Management

オーケストレーターは少なくとも次の状態を把握し続ける。

- Issue番号
- 作業ブランチ
- 各PaneのRole
- 各Roleに割り当てられたエージェント
- PR番号
- 現在のフェーズ
- レビュー回数
- 未解決レビュー指摘
- 各Paneの状態（待機中 / 作業中 / 完了）

次工程へ進む際は、必要な情報を明示的に対象ロールへ引き渡す。

## Completion Criteria

次をすべて満たした場合のみ完了とする。

- Issueの実装が完了している
- 必要なテスト・検証が完了している
- PRが作成されている
- PRへ最新の変更がPushされている
- レビューが完了している
- レビュー指摘がすべて対応済みである
- 未解決のConversationがない
- 最終レビューで追加修正なしと判断されている
- `review` がPRへ `LGTM` コメントを投稿している

完了条件を満たしたら、不要な作業ペインを終了し、Issue番号、ブランチ、PR番号、検証結果、レビュー回数を含む最終結果をユーザーへ報告する。
