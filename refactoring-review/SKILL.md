# リファクタリングレビュー

目的は保守性・可読性を高め、変更時の認知負荷を下げること。行数・ファイル数・関数数を減らすこと自体を目的にしない。DRY、KISS、YAGNI、単一責任を判断の補助に使い、機械的に適用しない。

## 進め方

1. AGENTS.md、仕様、ADR、テスト、実装を読み、対象範囲と維持すべき契約を確認する。
2. 呼び出し元、参照、状態遷移、外部依存を調査し、下記の観点で候補を抽出する。検索結果だけで未使用・到達不能と断定しない。
3. 各候補について現状の根拠、問題、最小の改善案、改善効果、影響範囲、検証方法を示す。根拠不足の候補は保留する。
4. レビュー依頼なら指摘に留める。実装依頼なら、小さな変更単位で進め、移動のみの差分とロジック整理を可能な限り分ける。
5. 既存の検証コマンドで確認する。未実施の検証は明示する。

## 確認観点

### 重複
- 同じ意味・判断を持つロジック、業務ルール、判定条件の分散
- 型ガード、バリデーション、データ変換、正規化、エラー処理の重複
- 同じ意味を持つ定数・設定値の重複、同一状態の多重管理
- 異なる名前で実装された同一処理
- 見た目が似ているだけで変更理由が異なる処理は共通化しない。

### 責務と依存
- 複数の責務が混在するファイル・クラス・関数、肥大化したコンポーネント
- UI描画と業務ロジック、HTTP層とインフラ層、データ変換と副作用の混在
- 状態管理とイベント処理の境界が曖昧な実装
- 不要な依存、循環依存、責務に対して広すぎる公開範囲
- サイズだけで分割せず、変更理由・責務・可読性を基準にする。

### 過剰設計・実装
- 将来の利用を想定しただけの抽象化、不要な基底クラス・インターフェース・デザインパターン
- 再利用性や可読性に寄与しない関数分割、単なる委譲ラッパー
- 不要な中間データ構造、過剰なジェネリクスや型定義
- 根拠のない防御的処理、信頼境界で検証済みのデータに対する無意味な再検証
- 実際に発生し得るエラーや回復処理の根拠がない try/catch
- 要件にないエッジケースへの対応。発生可能性、防止対象、追加複雑さを確認する。

### デッドコード・互換
- 未使用の関数・変数・型・定数・依存、到達不能コード、常に同じ結果の分岐
- 役割を終えたフォールバック、Feature Flag、コメントアウトされたコード
- 廃止仕様への互換分岐、利用者のいない互換レイヤー、旧パス維持だけの再エクスポート
- 動的参照、公開API、保存済みデータ、外部システムの版差・配布条件を調べてから削除を判断する。
- 互換削除が既存の契約を変える場合は別タスクとして承認を得る。

### 状態・制御フロー
- 派生値の独立した状態化、不要な同期、状態遷移の判断の分散
- 不整合な状態を表現できる構造、暗黙の実行順序依存
- 複雑なネスト、不要な非同期処理、タイマー・リスナー管理の分散
- Reactでは不要な useEffect、useMemo、useCallback を確認する。外部同期、cleanup、参照同一性の契約を壊さない。

### 命名・可読性
- 責務と一致しない命名、同じ概念に異なる用語、異なる概念に同じ用語
- 曖昧な名前、不要な略語、意味不明な数値・文字列
- 過剰なチェーン・三項演算子、追跡に多数のファイル移動が必要な実装

### コメント
- コードを読めば分かる What / How、コードを自然言語に言い換えただけの説明
- 関数名・変数名から自明な説明、意味のないセクション区切り、機械的に生成された冗長な説明
- **現在の実装と一致しないコメント**：古い処理順・条件・値・仕様、実際には保証していない振る舞い、廃止された設計前提
- 変更履歴、作業経緯、PRやレビューの会話、根拠や対応予定のない TODO / FIXME
- 不適切な命名や複雑な実装をコメントで補っている箇所
- 不一致は実装・契約・テストを突き合わせて指摘する。コメントだけを根拠に実装を変更しない。正しい契約が不明なら保留する。

### Docコメント
- 関数名の言い換え、型から自明な引数・戻り値の説明
- 内部関数への過剰な JSDoc / TSDoc、全関数・クラスへの機械的付与
- 実装詳細の逐一説明、自明な利用例、頻繁な同期更新を要する説明
- 実体と異なる引数・戻り値・例外、存在しない引数、廃止済みオプション
- 型定義や別のドキュメントとの無意味な二重管理
- 公開APIの利用契約、副作用、不変条件、例外、単位、非自明な制約やツールが必要とする注釈は維持する。

### テスト
- 実装詳細を固定するテスト、同一の振る舞いの重複検証
- 実質的な保証がないテスト、モック自体の検証、過剰なモック・スタブ
- 廃止済み仕様、発生し得ないケース、テスト名と内容の不一致
- テストのためだけの本番コードの抽象化
- 重要な振る舞いの検証は残す。既存の期待値を変えて回帰を正当化しない。

### ドキュメント
- 実装と一致しない README・ADR、廃止機能・設定・操作手順
- 同一仕様の分散、資料間の矛盾、成立しない設計前提
- 未実装機能を実装済みとする記述、Gitで追跡できる過去の経緯の過剰な記載
- 現行の判断を明確にしつつ、履歴保存が必要なADRはリポジトリの方針に従う。

## コメントの判断基準

- コードは How、テストは What、コミットやADRは Why を担う。
- インラインコメントは原則 Why not（なぜ自然な別案を採らないか）に絞る。
- 外部仕様・制約・非自明な契約や不変条件、必要な機械可読注釈は残す。
- 意味があるコメントは責務の移動先へ引き継ぐ。
- 実体に合わないコメントは、不要なら削除し、必要な契約なら正しい内容へ修正する。

削除候補の例:

```ts
// カウントをインクリメントする
count++;

/**
 * ユーザーIDからユーザーを取得する。
 * @param id ユーザーID
 * @returns ユーザー
 */
function getUser(id: string): User {
  // ...
}

// 最大3回リトライする
const MAX_RETRIES = 5;
```

残す価値のある例（実際の外部仕様を確認した場合）:

```ts
// 外部CLIが終了直前にstdoutへ結果を書き込むため、
// exitではなくcloseイベントを待つ。
```

## 共通制約

- 観測可能な振る舞いを維持する。UI・文言・HTTP status/error/header・保存形式・タイマー・操作順・外部契約など対象に応じて確認する。
- 仕様変更、不具合修正、契約を変える互換削除は別タスクとする。
- 新しい依存や抽象化を必要性なしに追加しない。
- 純関数の切り出し等では必要な振る舞いをテストし、対象リポジトリのテスト方針に従う。
- 形式、lint、型検査、既存テスト、必要な統合・E2Eを実行する。

## 出力

指摘ごとに、対象ファイル・行、観点、具体的な根拠、改善案、効果、影響・検証方法を記載する。優先度は実際の保守性や回帰リスクで判断し、単なる好みは指摘しない。振る舞いを変える候補と判断保留は分ける。実装した場合は変更内容と検証結果も示す。
