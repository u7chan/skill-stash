# React State Review

**目的は `useReducer` を増やすことではない。** 状態更新の意図・不変条件・変更箇所を追いやすくするために、最小の改善を選ぶ。

既定は**読み取り専用のレビュー**。明示的な依頼なしにコードを変更しない。

## 調査

1. 対象のコンポーネント・custom hook、React / React Nativeのバージョン、既存の状態管理・データ取得機構、関連する規約とテストを確認する。
2. 各 `useState` について、初期値、setterの全呼び出し箇所、更新条件、参照先を追う。イベントハンドラ、Effect、非同期コールバック、子へのsetter受け渡しも確認する。
3. ユーザー操作・非同期結果などの**出来事ごと**に、どのstateがどの順序・条件で更新されるかを整理する。相互依存、重複した更新規則、到達可能な不整合状態、reset経路を特定する。
4. 行数や `useState` の個数だけで結論を出さず、問題が生じる具体的なコード経路と、それを単純化できる設計を比較する。

## Decision Gate

以下の順で判断する。先の段階で十分に改善できるなら、Reducer化しない。

1. **state自体が不要か**: props / 他stateから導出できる値、重複したフラグは削除・導出を優先する。
2. **状態の所有者が違うか**: サーバーデータは既存のloader / Queryライブラリ等、外部storeは既存の購読機構、共有状態は適切な所有境界を検討する。Reducerはデータ取得や共有範囲の問題を解決しない。
3. **独立した単純な状態か**: 開閉フラグ、単独入力などは `useState` を維持する。複数あるだけでは移行理由にならない。
4. **遷移を集約する価値があるか**: 次のうち具体的な証拠があり、Actionとして表すことで改善するなら `useReducer` を推奨する。
   - 一つの操作で複数のstateを連動更新し、不変条件を守る必要がある
   - 同じ概念上の遷移が複数のhandler / Effect等に重複・分散している
   - 条件分岐・reset・非同期結果で遷移規則が複雑になり、変更漏れや矛盾した組み合わせが発生し得る
   - 状態遷移を純関数として切り出すことで、重要な振る舞いを独立して検証できる
5. **もっと適切な代替があるか**: 派生値の整理、単純な更新関数の共通化、状態所有者の変更、型付きunionによる状態表現、framework固有のフォーム・データ取得API等を比較する。厳密な遷移制約が必要な場合のみ状態機械も検討する。

### 判定区分

- **移行推奨**: 現行コードから不整合や更新漏れの経路、または重要な遷移規則の重複を示せ、Reducer化で明確に改善できる。
- **要検討**: 結合・分岐は複雑だが、改善効果や現在の不変条件がまだ確定しない。
- **別改善を推奨**: 問題はあるがReducer以外の最小変更で解決できる。
- **現状維持**: 独立・単純で、移行の利点が追加のActionや分岐より小さい。

想像上のエッジケースだけで「移行推奨」にしない。確認できた不具合と潜在的リスクは区別する。

## 移行案の作り方

移行推奨の箇所に限り、次を最小限で示す。

- **State**: 必須データと不変条件。排他的な状態は必要に応じてdiscriminated unionで表す。Reducer化だけで不正状態が排除されるとは考えない。
- **Action**: `started` / `succeeded` など「何が起きたか」を示す意味のある操作と必要なpayload。setterを1対1でActionに置き換えない。
- **Reducer**: `(state, action) => nextState` の純関数として、更新を一箇所に集約する。副作用・fetch・timer・乱数・外部store変更を入れず、元stateを破壊しない。
- **境界**: event / Effect / 非同期処理はReducerの外側に残す。独立したstateまで単一の巨大Reducerに押し込まない。
- **検証**: 重要な遷移・reset・不変条件を、既存テストと必要最小限のReducer単体テストで確かめる。

## レビュー出力

冒頭に結論と対象範囲を述べ、候補を優先度順に報告する。

| 優先度 | 場所 | 現状の更新経路・根拠 | 判定 | 最小の改善案 |
| --- | --- | --- | --- | --- |
| 高 / 中 | `path:line` | 実際のsetter / handlerと不変条件 | 移行推奨など | Action案または代替案 |

- 根拠はファイルと行番号を示し、確認できない関連呼び出しは未確認と明記する。
- 移行推奨には「想定するState / Action」「改善する不変条件」「回帰リスク」を添える。
- 対象がなければ「移行推奨なし」と明記し、指摘を作らない。
- 実装を依頼されたときだけ最小範囲を変更し、型チェック・関連テスト・lintを実行する。実行できない検証は明示する。

## Guardrails

- `useState` の数、コード行数、setterの受け渡しだけを問題としない。
- 自動バッチングを無視して「Reducerなら再レンダーが減る」と主張しない。
- Reducerを導入するためだけに不要な抽象化・ファイル分割・Actionを増やさない。
- Effect起因の問題は `react-effect-discipline` の判断基準、不要な複雑さは `development-simplicity-review` の方針と整合させる。
- Reactの新しいAPIを提案する場合は、実際の依存バージョンで利用可能か確認する。
